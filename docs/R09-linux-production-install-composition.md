# R09: packaged rootless Linux installation composition

## Scope and actual integration

`LinuxSettingsApplication.android(context)` now creates one `LinuxInstallCoordinator` beside the existing `LinuxSettingsController`. It still creates exactly **one** `TerminalUiOwner` from the startup catalog snapshot. `TerminalApplicationProvider` already calls this factory; it does not need a second provider/owner, and no MainActivity, ChatController, manifest, or Gradle file is changed here.

The existing Main route wiring is sufficient (keep its existing route/visit validity checks):

```kotlin
val application = (terminalProvider.state.value as? TerminalApplicationState.Ready)?.application
// Allocate once per route visit, outside composition:
val page = application?.settings?.enterPage()
// Existing Compose route:
if (application != null && page != null) {
    LinuxSettingsScreen(application.settings, page, onBack = { /* guarded navigation */ })
}
// At navigation commit / route replacement:
page?.close()
```

Main's existing `LinuxSettingsScreen(ready.application.settings, page, onBack = { ... })` invocation needs **no new argument**. All opening of approved Linux remains through `LinuxSettingsApplication.openLinux`, not a new owner. Do not construct another application on a page or after UNKNOWN.

## Runtime prerequisites and intentionally unsupported cases

The existing composition uses packaged `libproot_exec.so` and `libproot_loader.so` for arm64-v8a and x86_64 in jniLibs and the existing extracted native-library packaging. Artifact verification/bundling is parent-owned work; this recovery change does not recopy or alter any native binary, hash constant, manifest or shared artifact inventory.

These prebuilt helpers were built with eta_api=34. The provider explicitly rejects API 26–33, a 32-bit process, and machine ABIs other than aarch64/x86_64. The settings coordinator exposes `unavailableReason` and the page shows **Unavailable** with disabled install controls. App minSdk remains unchanged. **API26 Linux execution is unverified and requires a later rebuild/validation**; this is not compatibility evidence for manual external Linux configurations.

`PackagedProotHelperProvider.resolve()` reads only `context.applicationInfo.nativeLibraryDir`. It rejects writable/noncanonical files/directories, checks regular files, execute/read permission, bounded length and both exact hashes. The matching hash pair identifies the actually packaged ABI and must agree with the 64-bit process machine. No runtime helper download, chmod, PATH search or writable fallback exists.

## Explicit authority transitions

1. `LinuxSettingsPageOwner.prepareInstall(distribution, mirrorId)` selects only an entry from `LinuxRootfsCatalog` for the verified helper ABI, creates a fresh private target and freezes its full display. It cannot accept a URL, ABI, path or digest. This does not download or register.
2. `page.install(prepared)` checks object identity and obtains the installer's one-shot `DownloadInstallApproval` only in response to the first confirmation button. The existing downloader does not follow redirects or silently switch mirrors. GitHub-origin Debian URLs may therefore fail on a 3xx; the page explicitly warns about this and offers only separately selected fixed mirrors.
3. The real `AndroidLinuxInstallProbeRunner` executes `/bin/sh -c 'id -u'` under the prepared PRoot argv via `AndroidPtyHost.open`. This is an isolated diagnostic PTY, not a second terminal UI owner. There are no write/tool grants, shell fallback, root backend or selection changes. It bounds the accepted output to 4096 bytes and observation to 15 seconds (plus existing PTY startup and bounded termination waits). A successful result requires both a raw `wait_status` and `awaitTermination(true)`; `RootlessLinuxInstaller` additionally requires exit zero and trimmed stdout exactly `0`.
4. A published but unconfirmed receipt does not produce registration authority. `page.confirmPublishedDurability(prepared)` explicitly retries the same request. `RootlessLinuxInstaller.confirmPublishedDurability` requires its owner, exact marker, exclusive `.install-lock`, helper validation, tree synchronization, parent synchronization and a second marker inspection. `inspectPublished` by itself is still only inspection.
5. A durable receipt creates a separate `FrozenLinuxApproval`. The second explicit button calls `page.approveInstalled(frozen)`. Failed catalog persistence retains that **same object and generation**, including across page visits. Refreshing the catalog does not acknowledge the write. A rare pure-freeze failure retains the publication receipt and allows `prepareInstalledRegistration()` without reinstalling.
6. Successful registration is for the next application process only. Neither the current terminal startup snapshot nor its admission set is extended. Selection/open/terminal replacement is never performed by this flow.

Manual preview/approval and installation intent are mutually excluded by the controller. Revocation of a known reference is deliberately independent of installation recovery, pending registration, or UNKNOWN: it still synchronously denies new admission before catalog IO. A rejected remove request remains visible in the confirmation UI instead of silently dismissing it. Old page callbacks cannot act after revocation. The new installation state is app-owned, so leaving/reentering does not manufacture a new frozen approval.

## Cancellation and UNKNOWN

`page.cancelInstall()`, page revocation, and app teardown synchronously advance the coordinator admission epoch and invoke the actual `LinuxInstallCancellation.cancel()`. A queued registration checks its captured epoch/operation identity before any worker IO. After saving its non-authorizing description it passes a one-shot admission callback into the production catalog. The catalog invokes it exactly once after switching to IO and acquiring its real per-root gate, before the first catalog read/write. This callback and cancellation decide atomically on the short coordinator lock; no filesystem IO runs under that lock. Cancellation while waiting for the dispatcher or catalog gate therefore still rejects an unaccepted save. Leaving/closing fences an unstarted catalog mutation while retaining the original frozen object for an explicit current-page retry. Once the save is admitted, its success/failure receipt is retained even after revocation/close. This does not rely on cancelling an unrelated coroutine. Download cancellation closes/disconnects the active connection; probe cancellation requests closure of the owned PTY. Publication still uses the installer's cancellation/rename critical section. Cancellation cannot undo files already published or a registration write already started.

A missing raw wait status, unconfirmed termination, protocol UNKNOWN, or failed PTY startup with an owned cleanup handle raises `LinuxInstallProbeUnknown`. The runner retains the PTY/cleanup object; the installer strongly retains the exception and does **not** delete its staging/archive or `.install-lock`. The coordinator blocks retry/registration. No stale-lock auto-removal or output-based 'exit zero' inference exists. Such retained unknown resources currently require separate operator/host reconciliation; this change deliberately provides no unsafe 'force cleanup' button. Process death also does not authorize removal of the disk lock. The publication-retry API is not an UNKNOWN-cleanup API.

### Restart recovery (description, never authority)

The production coordinator starts with a worker-side **description recovery check** before it admits a new preview. The installer reconstructs metadata read-only; the coordinator additionally reconciles a matching catalog record and can durably retire a completed request. A failed check exposes `recoveryBlocked` and a read/verify-again button; neither a page refresh nor a new process permits generating another UUID to bypass the original operation.

* Preview preparation durably writes `filesDir/linux-installations/.install-request`: a bounded canonical description of the pinned catalog entry, exact mirror URL/hash/size/format, original environment/directory generation/private rootfs path and original packaged helper paths/digests. It does not serialize `DownloadInstallApproval`, consent, process-exit status or a successful publication receipt. Request publication uses a forced temporary file, atomic rename and parent fsync; these metadata writes do not execute the guest or contact any server.
* When a durable publication produces a registration preview (and again before the first possible catalog write), `.registration-request` in the original generation directory records the **same frozen catalog generation** bound to the request digest. The main request links that generation before catalog IO. Both records are descriptions, not grants. A missing linked registration description fails closed. A failed save/restart must not call `freezeForApproval` again to replace that generation. An identical existing registration file is forced again before its parent directory is synced and before the main request is linked; visible equal bytes alone are not a successful file-force receipt. In-process retries retain the exact `FrozenLinuxApproval` instance; restart reconstruction creates a new instance with identical contents. If the catalog has no matching record, registration still requires a new user click.
* Restart reconstructs an owner-bound `PreparedLinuxInstall` only by comparing the complete canonical record against the **current fixed catalog**, verified actual process ABI and **original helper pair at its original paths**. It checks their contents again. A changed catalog, missing/moved/tampered helper (including an APK update that changes its private library location), malformed/oversized/noncanonical journal, unexpected path, unresolved request temporary file, or missing journal with existing managed files blocks recovery. This is not a general import/migration tool, does not discover consent from markers, and does not substitute another helper or target.
* After catalog approval succeeds, the coordinator durably replaces the request with the empty-description tombstone. A crash between catalog commit and request retirement is reconciled on restart by matching the exact saved configuration, including generation, to the catalog and syncing its directory before retiring the request. **An inactive catalog tombstone also completes the request; it must never be reactivated.** This is not new consent, does not extend live admission, and deletes no rootfs or registration description. A failed retirement retains the original frozen request; its explicit retry accepts an already-recorded matching tombstone without resurrecting it.
* For a valid published target **without a matching catalog record**, recovery reads the exact original marker and contained shell; it exposes an **unconfirmed** publication, never a successful receipt. The user must explicitly choose same-path durability confirmation, which acquires a fresh writer lock, validates/syncs the original tree and parent, and rechecks the marker. It never downloads or replays `id -u`. Only then is the separate full registration approval enabled.
* For a valid untouched/unpublished request with no writer lock or residue, recovery shows the original request and permits only a newly confirmed download/install for that **same generation and target**, or an explicit safe discard. Discard writes a durable empty-description tombstone; it never deletes installed files or UNKNOWN resources.
* Any `.install-lock` or unexplained generation-local residue remains **UNKNOWN**, including after process restart. There is no PID guess, synthetic Drained result, replay, lock deletion, new-target workaround, or force-cleanup button. Missing/tampered published markers also block, rather than falling back to download. Recovery is deliberately strict: it does not recover pre-journal legacy installs, reconstruct lost metadata, repair partially written journals, prove a lost PTY exited, or automatically migrate an old helper path. These cases require separate audited operator/host reconciliation, not implicit application authorization.

Installer description recovery performs no mkdir, fsync, rename, delete, network request, probe, catalog freeze/write, selection, terminal opening, or admission update. Coordinator reconciliation only confirms a matching existing catalog record's directory durability and retires the non-UNKNOWN request with the normal forced-file/rename/directory-sync protocol; it never creates or reactivates catalog authority. UNKNOWN bypasses retirement and retains its original request identity and residue. The existing single application terminal owner, minSdk 26, and API34+/actual-64-bit installation gates remain unchanged.
